> ### v3（2026-09-25）第二轮评审结论
>
> **O-01 已闭环：库替换方案成立，且比预期简单得多。**
>
> 已核实 FCL 源码，其渲染器机制本质就是 `dlopen` 一个 GL 库：
>
> ```java
> // FCL/src/main/java/com/tungsten/fclauncher/FCLauncher.java
> bridge.dlopen(RendererPlugin.getSelected().getPath() + "/" + RendererPlugin.getSelected().getEglName());
> // 或内置渲染器：
> bridge.dlopen(nativeDir + "/" + config.getRenderer().getGlName());
> ```
>
> 对应的 `RendererConfigV2`（插件 APK 内 `@string/config` 资源中的 JSON）：
>
> ```kotlin
> data class RendererConfigV2(
>     val displayName: String,
>     val rendererId: String,
>     val rendererGLPath: String,       // 本项目提供的 libGL.so 填这里
>     val rendererEGLPath: String,      // 复用现有 EGL，不接管
>     val dlopenLibPaths: List<String> = emptyList(),
>     val env: List<EnvV2> = emptyList(),
>     val minMCVer: String? = null,
>     val maxMCVer: String? = null,
> )
> ```
>
> 结论：**不需要 LD_PRELOAD，不需要 inline hook，不需要修改启动器。** 本项目实现天然就是 FCL 的一个渲染器插件。
>
> ⚠️ 关于「无法完全关闭渲染器」的澄清：FCL 的「OpenGL 实现方式」不是可关闭的装饰层，而是**进程级 GL 库的绑定点**——不提供 GL 实现则 LWJGL 连符号都无法解析，游戏无法启动。因此正确做法不是「关闭渲染器让 mod 接管」，而是**让本项目的实现本身成为那个渲染器**。
>
> 其余新增决策：
>
> | 项 | 决策 | 理由 |
> |---|---|---|
> | 着色器兼容 | **尽最大努力兼容，无法兼容则降级**（不崩溃） | 用户明确要求；对应 §6 的 B+A 组合方案 |
> | EGL 接管范围 | **只提供 GL，复用现有 EGL** | 符合非目标；避免与 ANGLE 叠加造成双重翻译 |
> | 插件与 mod 关系 | **单仓多产物**：一份 native 核心 + FCL 插件 APK + NeoForge mod jar | native 逻辑只写一份，差异仅在包装层 |
> | FCL 插件时机 | **提前到阶段一并行**（原为阶段三 P3-07） | 插件路径性能优势明显，提前验证能更早暴露问题 |
> | Pojav 支持 | **降至阶段四** | Pojav 主仓库已归档，渲染器为 `Renderer.ID_*` 硬编码枚举，不支持动态插件 |
>
> **新增待验证项**：需实机确认 FCL 当前的 EGL 实现是否为 ANGLE。若是，则其 GLES 输出会再经 ANGLE 翻译一层，需相应调整策略。
>
> ### v4（2026-09-25）O-08 闭环：FCL 的 EGL 实现已核实
>
> 已阅读 FCL 源码确认其 EGL 机制，**不存在双重翻译风险**。
>
> `FCL/src/main/jni/ctxbridges/egl_loader.c` 的 `dlsym_EGL()`：
>
> ```c
> char* eglName = (strncmp(gles ? gles : "", "libGLESv2_angle.so", 18) == 0)
>                 ? "libEGL_angle.so"          /* 仅当显式指定 ANGLE 时 */
>                 : getenv("POJAVEXEC_EGL");   /* 否则由渲染器决定 */
> void* dl_handle = loader_dlopen(eglName, "libEGL.so", RTLD_LOCAL|RTLD_LAZY);
> /*                                          ^^^^^^^^^^^ 兜底 */
> ```
>
> **6 个内置渲染器中，5 个使用系统 `libEGL.so`，Zink 使用 `libEGL_mesa.so`；无一个使用 ANGLE。** 二者均为厂商/系统 EGL 实现（直接对接 GLES 驱动），非翻译层。
>
> 因此链路为：
>
> ```
> 我们的 libgl_gles.so（桌面 GL → ES 3.x 映射）
>     ↓ 输出原生 ES 调用
> 系统 libEGL.so + 厂商 GLES 驱动（原生执行）
> ```
>
> **结论：「不接管 EGL」的决策成立，无需修改。**
>
> ⚠️ **但发现一个必须处理的隐患（O-09）**：FCL 对内置渲染器会设置 `LIBGL_ES`（决定 EGL 上下文版本），但对**插件渲染器不设置**（`addRendererEnvInner()` 在插件分支直接 `return`）。而 `gl_bridge.c` 会读取它：
>
> ```c
> int libgl_es = strtol(getenv("LIBGL_ES"), NULL, 0);
> const EGLint egl_context_attributes[] = {EGL_CONTEXT_CLIENT_VERSION, libgl_es, EGL_NONE};
> ```
>
> **要求（P1-05）**：必须在插件 env 中显式声明 `LIBGL_ES=3`（作为 `NormalEnv`）。
>
> 另已确认 GL 库的加载方式：`FCLauncher` 会 `bridge.dlopen(getGLPath())` 预加载，Android 11 以下通过 `RENDERER_HANDLE` 环境变量向 LWJGL 的 `ndlopen` hook 传递句柄（插件路径含 `plugin` 字符串）。**因此本项目的库必须导出完整 GL 符号集**。

**目标**：为移动端 Minecraft Java 版开发一个 OpenGL ES 渲染后端模组，优先在 Android + NeoForge 1.21.1 + 原版/JEI 环境跑通，并通过软依赖兼容 Sodium（NeoForge 侧）/ Embeddium，实现自动检测、能力协商与功能降级。

---

## 1. 背景与目标

当前移动端 Java 版依赖 GL4ES/ANGLE 等兼容层，将桌面 OpenGL 翻译为 OpenGL ES，存在 CPU 开销大、帧生成不稳、部分模组兼容差的问题。本项目目标是开发一个**原生 OpenGL ES 渲染后端模组**，直接使用移动 GPU 的 ES 3.2 API，替代兼容层的高频渲染路径。

**核心策略**：不重写 Minecraft 渲染引擎，不替代 Sodium，而是作为“渲染后端适配层”，让原版和 Sodium 等优化模组在 ES 环境下**能跑、能降级、不崩溃**。

**主要场景**：近似原版 + JEI 等轻量辅助模组。  
**扩展目标**：软依赖联动 Sodium / Embeddium，自动禁用或降级无法在 ES 上运行的功能。

---

## 2. 范围与非目标

### 范围内
- Android 优先，目标 API：**OpenGL ES 3.2**，可选回退 ES 3.0。
- Minecraft **1.21.1 + NeoForge**，Java 21。
- 启动器：优先 **FCL（Fold Craft Launcher）**，兼容 PojavLauncher 及其分支（Amethyst-Android、ZalithLauncher 等）。
- 原版世界渲染、GUI、JEI 界面。
- 高频 GL 调用通过 **native 层实现**重定向到原生 GLES。
- 着色器从桌面 GLSL 转换为 **GLSL ES 320**（优先复用现有转换能力，见 §12）。
- 软依赖检测 Sodium / Embeddium，能力协商与降级路由。
- 剔除、粒子渲染控制、实例化渲染的 ES 适配。
- **FCL 渲染器插件**入口（可选增强路径，不在 MVP 范围）。
- 开源、可 fork、文档完整。

### 非目标
- 不实现完整 Vulkan 后端。
- 不追求光影、高级着色器、计算着色器全功能。
- 不修改 Minecraft 本体，不分发游戏资源。
- 不承诺初期性能超越 GL4ES。
- 不保证所有 Sodium 版本、所有设备完美运行。
- 不自行创建窗口/EGL 上下文；使用启动器已创建的上下文。
- **native 库不接管 EGL**，只提供 GL；EGL 复用启动器现有实现。
- 不重写完整的 GLSL → GLSL ES 转换器（优先复用兼容层已有能力）。
- **着色器兼容为「尽最大努力」而非「保证全覆盖」**：无法转换的着色器记降级事件并交回模组处理，不使游戏崩溃。
- **阶段四之前不保证 Pojav 主仓库（已归档）可用**。

## 4. 总体架构

```
┌─────────────────────────────────────┐
│ Sodium / Embeddium / 其他优化模组      │
├─────────────────────────────────────┤
│ Java 模组层（NeoForge Mod: glesmod）   │
│ - 能力探测 / 配置 / 兼容层 / 降级路由  │
│ - 状态上报 / 日志 / 设备兼容性数据库   │
├─────────────────────────────────────┤
│ native 后端（替代 libGL.so，C/C++）  │
│ - 桌面 GL ABI → GLES 3.2 映射        │
│ - 能力表 / 状态缓存 / FBO 与 VAO 仿真 │
├─────────────────────────────────────┤
│ LWJGL → libGL.so（本项目提供）        │
│ → libGLESv2.so                       │
├─────────────────────────────────────┤
│ Minecraft 1.21.1 / NeoForge / FCL     │
└─────────────────────────────────────┘
```

**关键机制**：
- **native 侧提供符号兼容的 `libGL.so` 替代实现**，内部转发到 `libGLESv2.so`。这是全链路的关键：LWJGL 在 Linux/Android 下动态链接 `<GL>`（即 `libGL.so`），启动器允许替换该库（GL4ES / NG-GL4ES 正是以这种方式工作）。
- 因此**不需要** LD_PRELOAD 或 inline hook：只要导出完整的 GL 1.x / 2.x / 3.x 符号集即可。风险在于符号覆盖不全，故需维护符号导出清单与覆盖率测试。
- Java 侧 Mixin 仅承担**低频高价值**职责：能力探测、兼容层联动、降级决策、日志上报。**不在热点路径上转发每一个 GL 调用。**
- 低频或暂未实现的调用在 native 侧内部回退到 GL4ES / MobileGlues（如可用）。
- 检测到 Sodium / Embeddium 时，启用更激进的降级与状态缓存策略。
- 能力接口通过 Java 侧暴露，供 Sodium 兼容层或未来的上游集成查询。

## 5. 关键接口与契约

### 5.1 能力提供接口

```java
public interface GlesCapabilityProvider {
    boolean supportsMultiDraw();
    boolean supportsComputeShaders();
    boolean supportsPersistentMapping();
    boolean supportsInstancing();
    int getMaxTextureUnits();
    int getMaxDrawBuffers();
    String getGlesVersion();
}
```

### 5.2 配置示例

```json
{
  "gles_compat": {
    "multi_draw": false,
    "compute_shaders": false,
    "persistent_mapping": true,
    "instancing": true,
    "max_draw_buffers": 4,
    "fallback_to_gl4es": true
  }
}
```

### 5.3 降级路由

> v1 此处写的是 Java 侧 `try/catch` + `GlesUnsupportedException`。native 路线落实后，**热点路径上的降级由 native 层内部完成**（不抛异常、不过 JNI），Java 侧只负责能力上报与日志。

**native 侧**：查询能力表决定路由，不可用时自动拆解为可用调用序列，并**只记录一次**降级事件：

```c
/* 能力表在初始化时填充，路由判断不涉及 JNI */
void glMultiDrawElements(GLenum mode, const GLsizei *count,
                         GLenum type, const void *const *indices,
                         GLsizei drawcount)
{
    if (g_caps.multi_draw) {
        g_real_glMultiDrawElements(mode, count, type, indices, drawcount);
        return;
    }
    /* 降级：逐次绘制 */
    for (GLsizei i = 0; i < drawcount; ++i) {
        if (count[i] == 0) continue;
        g_real_glDrawElements(mode, count[i], type, indices[i]);
    }
    GLES_COMPAT_WARN_ONCE(GLES_DEGRADE_MULTIDRAW,
                          "Multi-Draw 不可用，已降级为循环绘制");
}
```

**Java 侧**：只读地暴露能力与降级状态，供兼容层与日志使用：

```java
public interface GlesCapabilityProvider {
    // ... 见 5.1
}

// 降级事件由 native 层上报，Java 侧只负责读取与展示
List<DegradeEvent> events = GlesBackend.INSTANCE.getDegradeEvents();
GlesCompatLog.warnOnce("Multi-Draw 不可用，已降级为循环绘制");
```

> **P4-03 前置结论（2026-09-29，已核实）**：光照影**不是**本项目的瓶颈，
> 而是**上游版本配套问题**。真机实测：
>
> | 组合 | 结果 |
> |---|---|
> | Iris **1.8.12** + Sodium **0.8.13** | ❌ 进世界崩溃（`SodiumGameOptions$PerformanceSettings` 类不存在） |
> | Iris **1.8.14-beta.1** + Sodium 0.8.13 | ⏳ 未测（其 changelog 明确写「Updates to Sodium 0.8」） |
>
> **根因**：Sodium 在 0.8 把 `SodiumGameOptions` 重构为 `SodiumOptions`，
> 而 Iris 1.8.12 的 Mixin 仍指向旧类名 → `ClassNotFoundException`。
> **崩溃发生在 Mixin 阶段（Java 侧），与本项目的 GL 后端无关**
> （同日日志显示我们的 `降级事件/缺失符号/被调用的空实现` 均为 0）。
>
> **⇒ 在 Sodium 0.8.13 基线上，光影只能靠 Iris 1.8.14-beta.1。**
> 详见 `docs/known-issues-iris.md`。

> **另注**：`Oculus` 已停更，且其 1.21.1 移植版质量极差，**不纳入评估范围**。

> ### v5（2026-09-25）O-02 闭环：工作量大幅下修
>
> 通过 `native/tools/` 下的四个脚本完成量化分析，详见 `docs/o-02-symbol-inventory.md`。
>
> **核心数据**：
>
> | 指标 | 原估算 | 实测 |
> |---|---|---|
> | 需导出符号数 | 316（GL 3.2 core 全集） | **89** |
> | GLES 可直接满足 | — | **79（88.8%）** |
> | 需额外适配 | 约 82 | **5（5.6%）** |
>
> **四项重大发现**：
>
> 1. **MC 只用到 GL 3.0**，未引用 `GL31`/`GL32` 或更高绑定类。这意味着 **ES 3.0 即可满足原版**，ES 3.2 是充裕的。
> 2. **原版不使用任何 ES 受限高阶功能**：Multi-Draw、计算着色器、间接绘制、持久映射、同步对象、实例化渲染——**全部未使用**。
> 3. **5 个需适配的符号经调用链追踪确认非关键路径**：`glGetTexImage`/`glDrawPixels` 仅用于图像回读（`NativeImage` 类），不在每帧渲染循环。
> 4. `glDrawPixels`、`glLogicOp`、`glPolygonMode`、`glClearDepth` 均可 stub 或简单转换，MVP 必需部分仅约 25 行代码。
>
> **据此调整**：
>
> - P1-04 符号导出范围锁定为 **89 个**（见 `docs/o-02-symbol-inventory.md`），不追求 GL 3.2 core 全集
> - P2-04（Multi-Draw / 计算着色器 / 持久映射降级）**从 P0 降为 P1**，它们仅服务于 Sodium 路径，不阻塞 MVP
> - ES 版本目标可放宽：MVP 为 ES 3.0，ES 3.2 作为增强（降低 R-11 风险）
>
> ⚠️ **v6 之后的事实修正（2026-09-29）**：v5 给出的「89 个」是**原版 MC 直接引用**的符号数。
> 实机跑通后发现，**LWJGL 的 `createCapabilities()` 会解析它声明的全部 native 方法**，
> 缺失任何「必需函数」都会抛 NPE 硬崩溃（真机已两次踩到）。
> 因此实际导出量必须覆盖 LWJGL 的完整声明集，最终为 **849 个**（345 转发 + 20 定制 + 484 stub）。
> 详见 `native/symbols.def` 头部说明与 `docs/status-report.md` §5。
>
> ### v6（2026-09-29）阶段一、二完成；两处定向修复
>
> **阶段一与阶段二均已完成并通过真机验收。** 详见 `docs/status-report.md`。
>
> | 项 | 结论 |
> |---|---|
> | 主菜单 / 世界 / Sodium | ✅ 全部跑通，**零渲染错误** |
> | 性能 | ✅ 与 MobileGlues / Zink **相当**（原版环境几乎无差别），非「超越」 |
> | P2-04 / P2-05 / P2-07 | ✅ 三份文档已补齐 |
> | `glBufferStorage` | ⚠️→✅ 从静默 stub 改为**真实分配 + 降级**（原会导致 Embeddium 崩溃） |
> | `glMapBufferRange` | ⚠️→✅ 剥离 ES 非法的持久/一致映射位后转发 |
>
> **由此新增的一条设计原则**（值得写入长期约定）：
>
> > **静默 stub 只适用于「调用方不会依赖其返回值/副作用」的函数。**
> > 若函数的契约包含产生某种资源（分配存储、创建对象、返回句柄），
> > 做成静默 stub 就等于**用一个谎言替换一次失败**，而谎言会在很远的地方以完全无关的形式暴露。
>
> **据此需修订 v5 的第 4 条**：「均可 stub 或简单转换」这一判断过于乐观 ——
> **stub 的适用性必须逐个按「调用方是否依赖其副作用」来判定**，不能一概而论。
>
> **R-06「性能不如 GL4ES」已可作废**（实测与 MobileGlues / Zink 相当），
> 但仍未做严格 A/B 对比，
> P1-09（可复现基准脚本与 CSV）仍应完成，才能给出严格结论。
>
> **新增遗留审计项 R-12**：其余 484 个 stub 尚未逐一审计是否存在同类问题。

## 10. 开源与协作策略

- **许可证**：LGPL-3.0-or-later。
- **README**：目标、非目标、构建、测试、已知限制、性能数据。
- **模块化**：Java 模组层（能力/配置/兼容层）、native 后端层（GL 映射/状态缓存）、构建接入层，三者独立。
- **CI/CD**：GitHub Actions 自动构建 jar；native 交叉编译需 Android NDK，先在本地验证后再接入 CI。
- **Good First Issue**：补充文档、添加基准脚本、补充符号导出清单条目。
- **性能基准**：原版生存、JEI 搜索、箱子界面，记录 FPS、帧生成时间、CPU 占用。
