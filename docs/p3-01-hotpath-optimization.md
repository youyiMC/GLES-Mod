# P3-01：native 热路径开销优化

> 状态：✅ **已完成并真机验证（正确性）**；⚠️ 性能收益**尚无实测数据**
> 日期：2026-09-29
> 对应任务：P3-01（native 侧减少冗余调用 / 降低每调用开销）
> 起点：`docs/status-report.md` §4.3.1 指出「`state_cache` 只是一个空开关」
> 工具：`native/tools/hotpath_cost.py`（反汇编实测，无参）

---

## 1. 一句话结论

**每个 GL 调用到达驱动前要执行 29 条指令，其中只有 5 条是必要的。** 实测后优化到 **15 条**；
含探针的函数从 **534 条 / 496 字节栈帧**降到 **65 条 / 64 字节栈帧**。

---

## 2. 为什么先做「测量」而不是先做「优化」

任务书 P3-01 写的是「native 侧状态缓存，减少冗余 GLES 调用」。但直接动手写状态缓存
有几个问题：**状态缓存要处理哪些函数、有多少冗余可省，全都是未知数**；
而写错一个状态缓存的后果是**渲染错误**（缓存与实际 GL 状态不一致）—— 风险高、收益未知。

相比之下，有一类开销是**确定的、全量适用的**：每个转发函数在到达驱动之前都要执行的
固定代码。原版 MC 每帧有 $10^4 \sim 10^5$ 次 GL 调用，因此这部分开销**乘以 10 万**就是每帧的净损失。

**代码注释里多次写过「开销可忽略」，但从没有人量过。** 所以我先量。

---

## 3. 实测基线（优化前）

`native/tools/hotpath_cost.py` 用 NDK 的 `llvm-objdump` 反汇编 optimized 产物。

### 3.1 `glBindTexture`（每次调用 29 条指令才到达驱动）

```asm
 1  stp   x29, x30, [sp, #-0x30]!   <- 建立栈帧
 2  str   x21, [sp, #0x10]          <- 保存 callee-saved
 3  stp   x20, x19, [sp, #0x20]!    <- 再保存两个
 4  mov   x29, sp
 5  mov   w19, w1                   <- 参数暂存
 6  mov   w20, w0                   <- 参数暂存
 7  bl    <glesmod_lazy_init@plt>   <- ★ 跨编译单元 PLT 调用 ★
 8  adrp/ldr/ldr/cbz                <- 读 trace_enabled 并分支（4 条）
14  bl    <glesmod_trace_call@plt>  <- 追踪调用
15-17 adrp/ldr/cbnz                 <- 取缓存的函数指针并判空
18-23 （仅首次：解析 + 存储 + 判空）
24-28 mov/ldp/ldp/ldp               <- 恢复寄存器
29  br    x2                        <- 真正调用 GLES
```

**第 5、6 条之所以存在，仅因为第 7 条要跨编译单元调用** —— 编译器必须保住参数不被破坏。
这是**函数调用本身**带来的成本，由 `bl` 触发。

### 3.2 量化

| 项 | 数值 |
|---|---|
| 每帧 GL 调用次数（估算） | $5 \times 10^4$ |
| 可省序言 | 约 24 条 |
| 每帧多执行 | $1.2 \times 10^6$ 条 |
| 折算时间（P1–P8 各 1 条/周期 @2.3GHz） | **约 0.2 ms/帧** |
| 在 300 FPS（3.3 ms/帧）中占比 | **约 6%** |

> **同时发现的第二个问题**：`glDrawElements` 因探针代码内联，被迫保留
> **496 字节栈帧 + 12 个 callee-saved 寄存器 + 栈保护金丝雀**（17 条纯序言），
> 而探针**默认是关闭的** —— 这段代码在正常情况下一次都不执行。

## 4. 改动

### 4.1 用 `GLESMOD_HOTPATH` 取代 `glesmod_lazy_init()` + `GLESMOD_TRACE()`

```c
/* 稳态：一条分支，可内联，无函数调用、无栈帧 */
#define GLESMOD_HOTPATH(name)                                        \
    do {                                                             \
        if (__builtin_expect(glesmod_hotpath_ready, 1) == 0) {       \
            glesmod_on_first_call(name);                             \
        }                                                            \
    } while (0)
```

**关键点：用「一个标志位」同时承载两种语义。**

| 模式 | `glesmod_hotpath_ready` | 稳态行为 |
|---|---|---|
| `GLESMOD_TRACE=0/1`（默认） | 初始化结束后置 1 | 零钩子开销 |
| `GLESMOD_TRACE=2`（深度追踪） | **永不置位** | 每次调用都记录完整序列 |

这样两种模式**只共用一条分支**。若用两个独立变量（「初始化完成」+「是否需要追踪」），
稳态下就要多一条分支和一次内存读 —— 那正是本次要去掉的东西。

### 4.2 把探针主体移出热函数

```c
__attribute__((noinline))
static void probe_on_draw(GLenum mode, GLsizei count) { ... }

void glDrawElements(...) {
    if (__builtin_expect(g_probe_ready, 1) == 0) { ...一次性检查... }
    if (g_probe_on) probe_on_draw(mode, count);   /* 默认不跳 */
    PROBE_RESOLVE_OR_RETURN(real, "glDrawElements", );
    real(mode, count, type, indices);
}
```

### 4.3 新增 `GLESMOD_TRACE=2` 深度追踪档

**这是对一处诊断能力回退的补偿，必须说明。**

优化把「记录调用序列」从全时段缩减为「初始化阶段」。这**确实削弱了**
「记录崩溃前调用序列」的能力。虽然真机两次 SIGSEGV 都在早期初始化阶段
（默认档已覆盖），但「长时间运行后崩溃」这类问题仍需要完整序列。

因此保留一个显式开关：

| 取值 | 含义 | 代价 |
|---|---|---|
| `0` | 关闭追踪 | 无 |
| `1` | **默认**。只追踪初始化阶段 | 稳态零开销 |
| `2` | 深度追踪，每次调用都记录 | 每调用多一次分支 + 一次原子自增 |

## 5. 实测结果

| 符号 | 总指令（前 → 后） | **稳态（前 → 后）** | 说明 |
|---|---|---|---|
| `glBindTexture` | 35 → 44 | **29 → 15** | 去掉跨编译单元调用与参数暂存 |
| `glUniform1i` | 35 → 44 | **29 → 15** | 同上 |
| `glUniformMatrix4fv` | 42 → 55 | — → **17** | |
| `glVertexAttribPointer` | 49 → 66 | — → **40** | |
| `glDrawElements` | **534 → 65** | **36 → 27** | 栈帧 496B → 64B；探针改为 noinline |
| `glBindBuffer` | 35 → 44 | **29 → 15** | |
| `glEnable` | 30 → 37 | **25 → 13** | |
| `glActiveTexture` | 30 → 37 | **25 → 13** | |

**注意「总指令数变大」不是退步**：多出来的部分是**永不执行的慢路径**
（首次调用 / 解析函数指针 / 找不到符号），编译器把它们甩到函数尾部，
使稳态路径更紧凑。这正是期望的代码布局。

## 6. 正确性保障

| 关注点 | 处理 |
|---|---|
| 初始化仍能重试 | `glesmod_hotpath_ready` **只在初始化真正结束**（探测成功**或**已放弃重试）后置位；探测中不置位，避免永久跳过重试 |
| 崩溃定位能力不丢失 | 首次调用仍会写入 `g_trace_ring`；需完整序列时用 `GLESMOD_TRACE=2` |
| 未启用后端时 | `!g_enabled` 也视为「已完成」，不反复走慢路径 |
| 探针开关语义 | `GLESMOD_GEOM_PROBE` 由启动器在 `dlopen` 前注入，进程内不变，可安全缓存 |
| 无数据竞争 | 标志位为 `volatile int`，只在初始化结束时写一次；极端情况下读到 0 只会多跑一次**幂等**的 `lazy_init` |

## 7. 工具的已知局限（诚实标注）

`hotpath_cost.py` 的稳态路径推断**基于 AArch64 的反汇编格式**。
对 `armeabi-v7a`（ARM32）产物，分支指令写法不同，推断失效 ——
表现为「稳态 ≈ 总指令数」（如 37/40）。

**那是工具的局限，不是真实回归。** ARM32 的可信判据只有
「`lazy_init` 是否为『无』」（实测两者均为「无」，即已优化）。
报告中已显式标注这一点，避免误读。

> **原版环境**下，**GLES Mod + Sodium** 与 **MobileGlues + Sodium**、

#### 这条结论的含义（以及它的边界）

| 维度 | 判读 |
|---|---|
| 与其他渲染器**并列** | ✅ 可声称 |
| **超越**其他渲染器 | ❌ **不可声称** |
| 相对**改动前**的提升 | ❌ **无数据** |

#### ★ 它推翻了我之前一处表述 ★

我曾在 `docs/status-report.md` §7.3 写过「GL4ES 在同类设备上通常为 30~60 FPS」，
并据此说本项目「远超基线」。**那条对比不成立，已删除。** 理由：

| 问题 | 说明 |
|---|---|
| 参照对象不对 | GL4ES 是**旧一代**翻译层；当前主流已变成 **MobileGlues / Zink**，它们同样成熟高效 |
| 数据来源不实 | 「30~60 FPS」是我凭印象写的，**没有一手测量来源** |
| 由此得出的结论过强 | 既然参照数不可靠，「远超」就不能成立 |
| 且与用户实测**直接冲突** | 用户实测：三者**几乎没有差别** |

⇒ 正确的表述是：**「与其他主流渲染器相当」，而不是「超越」**。

#### 这个结果其实**不意外**，而且指向同一结论

MobileGlues（GL→ES 转发层）与 Zink（GL→Vulkan）都在 **native 层**，
与本项目处于**同一层次**，并且都直接调用 GPU 驱动。
三者在**原版 + Sodium** 这类负载下表现相近，是符合预期的。

**但要注意**：本项目的差异化点**不在帧率** —— 而在于：

| 本项目 | MobileGlues | Zink |
|---|---|---|
| 直接输出 **ES 3.2** | 输出 ES（同样是转发层） | 经 **Vulkan** 再翻译一层 |
| **不引入中间层** | 需 GL→ES 翻译 | 需 GL→Vulkan 翻译 |
| 与模组的**能力协商**（降级可见） | — | — |

⇒ 「原版环境几乎无差别」说明**链路本身是健康的**
（没有翻译层被重复叠加、没有引入额外开销）；
而差异应体现在**更极端负载**下（光影、大型模组包、高视距）。

#### 必须明确的未验证项

| 项 | 状态 |
|---|---|
| 「无差别」的具体场景 | ⚠️ 仅限**原版 + Sodium**；其他负载未测 |
| 「无差别」的具体数值 | ⚠️ 只知道「几乎」，**没有 FPS 数字** |
| 相对**改动前**的提升 | ❌ **完全无数据** —— 未做改动前/后同场景对照 |

> **严守分界**：「指令数 29 → 15」是**事实**（反汇编可复核）；
> 「与其他渲染器相当」是**用户实测的横向结论**；
> 「帧率提升了 X%」**仍然没有数据**。三者不可混为一谈。

## 9. 与任务书 P3-01 的关系

任务书 P3-01 的原文是「native 侧状态缓存，减少冗余 GLES 调用」。

本次做的是**其中一条路径**：消除每个调用上的固定开销。
而**真正的「状态缓存」**（缓存 GL 状态以避免冗余的状态设置调用，如
连续两次 `glBindTexture` 同一纹理时跳过第二次）**尚未实现** ——
它需要为每个状态类维护影子状态，风险与工作量都显著高于本次改动。

**建议**：本次改动落地并真机验证后，再决定是否推进状态缓存。
理由：状态缓存写错会导致**渲染错误**（缓存与真实 GL 状态不一致），
而本次改动**不改变任何 GL 语义**，是低风险高确定性的那部分收益。
先把低风险收益拿掉，再评估高风险的。

## 10. 复现方法

```powershell
# 构建产物
.\build-all.ps1

# 测量（也会在 build-all.ps1 里作为信息性报告输出）
py native\tools\hotpath_cost.py
```
